Implementation Notes — Phase 3

speakeasel · 2026-09-02 · Tool Surface: 14+ WebMCP tools over the frozen scene layer, activity feed, contract-pinned suite

adapter.ts — optional annotations field added (scope addition)

Context
The spec wants annotations: { readOnlyHint: true } on get_canvas_state and describe_canvas, but ToolDef in src/webmcp/adapter.ts had no such field and adapter.ts is not in the spec's Modified Files list.
Decision
Added one backward-compatible optional field annotations?: Record<string, unknown> to ToolDef — the route the scout's context map explicitly blessed as "a defensible scope addition". registerAll registers try-with-annotations and, on a throw, re-registers the def without the field (safe: the failed attempt never landed).
Alternative
An as any cast local to tools.ts — rejected as it hides the field from the shim/test surface and from any future consumer of ToolDef.

tools.ts — surface is 15 tools, not 14

Context
The spec's tool table has 14 rows with undo / redo sharing one row, then says "(14 total counting undo and redo separately)" — arithmetically that makes 15 distinct tools.
Decision
Implemented every named tool in the table: 13 single-row tools + undo + redo = 15 registered tools. The contract criterion (tools.size >= 14, both read tools pinned by name) is satisfied either way; dropping a named tool to hit exactly 14 would violate the table.
Alternative
Merging undo/redo into one tool with a direction argument — rejected: the spec's decision log requires undo always registered as its own tool ("static undo in MVP").

index.html — listed as modified, needed zero changes

Context
The spec's Modified Files table lists index.html ("Activity feed mount"), but <section id="activity"> already exists at line 37 — it landed in Phase 2's markup pass, exactly as the scout's context map flagged.
Decision
No edit made; main.ts mounts the feed on the existing section. Adding a second mount would duplicate the DOM id.
Alternative
None viable — a duplicate section would break the querySelector contract.

undo/redo — "Undid: …" phrased as summary restatement, no label stack

Context
The spec's tool table sketches the undo response as "Undid: …" from history, but the frozen scene layer keeps unlabeled snapshots — there is no per-entry description to quote, and adding one would modify scene.ts (explicitly not in this phase's file set).
Decision
The tool returns Undid the last edit. Now: {one-line state summary} — honoring the spec's "response texts always restate the resulting state fragment" rule without touching the frozen store. Empty history returns exactly Nothing to undo yet. as specified.
Alternative
A parallel label stack inside tools.ts mirroring scene history — rejected: it would desync from renderer/toolbar-originated mutations that never pass through the tool layer.
